## Architecture Snapshot

- The workspace is intentionally small: one binary crate, no external dependencies, no separate library crate.
- [main.rs](/C:/dev/rust_agent/crates/app/src/main.rs:12) is the application surface. It parses CLI input, builds audit requests, resolves target paths, persists reports, prints help/errors, and decides exit behavior.
- [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:103) is the runtime adapter. It defines request types, resolves the Codex executable, mutates `PATH`, detects git presence, spawns child processes, polls temp files for the final message, enforces timeouts, and handles process termination.
- Error handling is split between a custom parse result in [main.rs](/C:/dev/rust_agent/crates/app/src/main.rs:44) and `io::Result`-based runtime behavior in [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:103). There is no async runtime; subprocess orchestration is a blocking poll loop in [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:207).

## Key Findings

### [High] `main.rs` carries too many reasons to change

Evidence: [main.rs](/C:/dev/rust_agent/crates/app/src/main.rs:57), [main.rs](/C:/dev/rust_agent/crates/app/src/main.rs:119), [main.rs](/C:/dev/rust_agent/crates/app/src/main.rs:253), [main.rs](/C:/dev/rust_agent/crates/app/src/main.rs:315), [main.rs](/C:/dev/rust_agent/crates/app/src/main.rs:338), [main.rs](/C:/dev/rust_agent/crates/app/src/main.rs:371).

Risk: CLI parsing, audit policy, filesystem validation, report persistence, and process-exit behavior are coupled in one file. Any new subcommand, audit option, or report behavior now edits the same switchboard, which raises change cost and makes regressions more likely.

Refactor direction: keep `main` as wiring only; extract small concrete modules for `cli`, `audit_prompt`, and `report_store`. Shared option parsing for `model`, `reasoning`, and `verbose` should move into a reusable helper instead of being maintained twice.

### [High] `codex.rs` mixes domain types, environment discovery, and subprocess control

Evidence: [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:68), [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:136), [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:207), [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:413), [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:431), [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:544).

Risk: request modeling, argument construction, executable lookup, VS Code path scanning, git detection, timeout behavior, temp-file capture, and process-tree termination all live together. That lowers cohesion and makes it hard to change one operational concern without touching unrelated logic.

Refactor direction: split by responsibility, not by abstract pattern: `request/args`, `discovery`, and `runner` are enough. Keep concrete types unless a second execution backend actually appears.

### [Medium] The most failure-prone runtime boundary is only lightly protected by tests

Evidence: production behavior lives in [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:173) and [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:207), while existing tests are concentrated in [main.rs](/C:/dev/rust_agent/crates/app/src/main.rs:385) and [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:576).

Risk: the suite proves parser behavior and a few helper functions, but it does not exercise spawned-process behavior, timeout handling, report persistence, repo-detection behavior, or the “final message arrives before process exit” contract. That makes structural refactors around execution flow risky.

Refactor direction: add black-box tests using a fake executable that can emit a final-message file, delay exit, time out, and write stderr. Do that before moving logic across modules.

### [Low] Environment-specific logic is duplicated and slightly brittle

Evidence: VS Code extension scanning exists in both [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:488) and [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:558); git detection is a manual `.git` existence walk in [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:544).

Risk: search-policy changes must be updated in two places, and repository detection may not behave as expected for worktrees or `.git` file layouts. This is not the main design problem, but it is avoidable maintenance debt.

Refactor direction: centralize extension discovery behind one iterator/helper and harden repo detection with a more explicit policy plus tests for non-repo and alternate repo layouts.

## Principle Review (SOLID / DRY / KISS / YAGNI)

- `SOLID`: the main tension is Single Responsibility at module level. [main.rs](/C:/dev/rust_agent/crates/app/src/main.rs:1) and [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:1) each combine multiple reasons to change. Dependency inversion is not the main gap here; adding traits just to satisfy DIP would be premature.
- `DRY`: there is meaningful duplication in the two argument parsers and in Codex/VS Code discovery logic. Outside that, duplication is limited and mostly acceptable for a small binary.
- `KISS`: the project is mostly simple and concrete, which is good. The main exception is the process lifecycle path in [codex.rs](/C:/dev/rust_agent/crates/app/src/codex.rs:207), where polling, temp files, timeout behavior, and forced termination make intent harder to verify.
- `YAGNI`: the code currently shows healthy restraint. There are no speculative repositories, service traits, or framework-style layers. Refactoring should preserve that and focus on cohesion first, not architecture theater.

## Refactoring Roadmap

1. Stabilize  
Add integration-style tests around subprocess execution, timeout behavior, final-message capture, non-git workspaces, and audit report persistence. Document whether a final message is considered authoritative even when the child exits non-zero.

2. Simplify  
Split `main.rs` into CLI parsing and audit/report concerns. Split `codex.rs` into request/args, environment discovery, and process running. Consolidate duplicated flag parsing and duplicated VS Code extension scanning.

3. Reshape  
Only if this tool is expected to grow beyond one small binary, introduce a thin application service or library boundary for orchestration. Keep concrete implementations until there is real pressure for multiple backends or alternate storage/report targets.

## Open Questions / Validation Needed

- Is “report exists even when Codex exits non-zero” an intentional success model for audits, or just a tolerated edge case in [run_audit](/C:/dev/rust_agent/crates/app/src/main.rs:253)?
- Does this wrapper need to support git worktrees, `.git` files, or symlink-heavy targets, or is simple directory-based repo detection sufficient?
