# Architecture Snapshot

This is a minimal Rust workspace with one crate, `app`, whose job is to wrap Codex CLI workflows for audit, planning, implementation-audit, adversarial review, fix-loop, and workflow automation.

Main seams as implemented:
- CLI surface and top-level orchestration live in `crates/app/src/main.rs`.
- Codex process launching, timeout handling, temp-file capture, executable discovery, and Git-repo detection live in `crates/app/src/codex.rs`.
- JSON workflow parsing and step execution live in `crates/app/src/automate.rs`.
- `plan.rs`, `review.rs`, `implementation_audit.rs`, and `fix_loop.rs` mostly provide path validation, prompt construction, and artifact saving wrappers.
- Artifact persistence is centralized in `crates/app/src/artifact.rs`.

Dependency direction is simple but highly centralized:
- `main.rs` depends on nearly every other module and still owns most command knowledge.
- `automate.rs` depends on `codex` configuration types and recursively invokes the current executable rather than calling command handlers as library functions.
- Workflow coordination depends on parsing human-readable stdout and Markdown content rather than typed result objects.

The codebase is small enough that heavy layering would be unnecessary, but the current design already concentrates too much behavior into a few string-driven orchestration paths.

# Key Findings

## [High] `main.rs` is a command god-module that mixes parsing, workflow policy, prompt authoring, execution, and persistence

- Evidence: `crates/app/src/main.rs:1-1283`; especially `parse_audit_args` at `174-252`, `parse_plan_args` at `254-348`, `parse_implementation_audit_args` at `350-468`, `parse_review_args` at `470-589`, `parse_fix_loop_args` at `591-710`, and the mirrored `run_*` functions at `909-1178`.
- Risk: the main command surface has multiple reasons to change at once: CLI syntax, default timeouts, path resolution, prompt wording, persistence rules, and execution policy. That raises regression risk whenever a new command or option is added, because behavior is spread across repeated parse and run branches rather than modeled once.
- Refactor direction: introduce a small command descriptor layer so each service command declares its parse rules, prompt builder, timeout default, and artifact saver in one place. Keep `main.rs` as dispatch only.

## [High] Workflow orchestration is brittle because it depends on parsing human-facing stdout and Markdown markers instead of typed step results

- Evidence: `crates/app/src/automate.rs:150-197` (`run_workflow`), `380-387` (`extract_artifact_path`), `389-402` (`is_clean`), plus `workflows/refactor.json` clean markers and the `" enregistre dans "` output convention expected from command handlers in `main.rs`.
- Risk: automation success depends on exact phrasing in terminal output and report text. A harmless wording change in a printed line or final audit sentence can break artifact chaining or loop termination. That is a correctness and evolvability problem, not just style debt.
- Refactor direction: return structured machine-readable step outcomes for internal workflow execution. At minimum, separate human output from a stable artifact/result channel; ideally invoke internal handlers directly instead of shelling back into the current executable and scraping stdout.

## [Medium] Command knowledge is duplicated across multiple switchboards, creating avoidable drift pressure

- Evidence: subcommand recognition is repeated in `main.rs:72-108`, help text in `main.rs:829-888`, `automate.rs:316-378` (`command_accepts_codex_options`, `command_is_direct_run`, `known_subcommand`), prompt builders across `main.rs`, `plan.rs`, `review.rs`, `implementation_audit.rs`, `fix_loop.rs`, and workflow assumptions in `workflows/refactor.json`.
- Risk: adding or renaming a command requires synchronized edits in several places. Missing one produces inconsistent behavior that the compiler will not catch, especially for automation and help output.
- Refactor direction: define subcommands and their capabilities once, then derive parsing/dispatch/help/automation metadata from that source. This can stay lightweight; the project does not need a framework, just one authoritative registry.

## [Medium] The boundary modules are thin wrappers, so responsibility was split by file without actually reducing coupling

- Evidence: `plan.rs`, `review.rs`, `implementation_audit.rs`, and `fix_loop.rs` mainly contain a command struct, path resolution, a prompt builder, and an artifact saver; the real lifecycle logic remains in `main.rs`.
- Risk: the code looks modular at the file level, but behavior is still centralized. That creates false confidence: future changes still require editing `main.rs` plus one wrapper module, so cohesion has not materially improved.
- Refactor direction: move end-to-end command behavior behind module-level entry points or service structs, so `main.rs` no longer knows how each command validates paths, builds prompts, runs Codex, and saves artifacts.

## [Medium] Test coverage protects parsing and string assembly well, but not the fragile process and workflow boundaries where refactors are most risky

- Evidence: 57 passing unit tests are concentrated in parser, prompt, and helper behavior; there are no integration-style tests around `run_workflow`, stdout artifact extraction, loop-stop conditions, or Codex process timeout/error handling.
- Risk: the most failure-prone seams are external-process orchestration and recursive workflow execution, but those seams have the weakest protection. That makes structural refactoring harder to do safely.
- Refactor direction: add focused integration tests for workflow execution contracts and for the machine-readable artifact/result boundary before reshaping modules.

# Principle Review (SOLID / DRY / KISS / YAGNI)

**SOLID**
- `S`: violated most clearly in `main.rs`, which mixes CLI parsing, runtime orchestration, persistence, and prompt authorship.
- `O`: moderate tension from repeated command switchboards. New behavior currently requires editing several central branches.
- `L`: no major confirmed trait-contract issue; the code uses few traits and avoids polymorphism-heavy surprises.
- `I`: not a major concern today; interfaces are mostly concrete.
- `D`: workflow logic depends directly on volatile human-facing IO strings (`stdout`, Markdown clean markers) instead of a stable internal boundary.

**DRY**
- Real duplication exists in command parsing and execution scaffolding across `main.rs`, and in command recognition metadata duplicated between `main.rs` and `automate.rs`.
- Small helper duplication is not the main problem; the costly duplication is behavioral knowledge that can drift.

**KISS**
- The overall feature set is small, but the implementation uses a more indirect route than necessary for workflows by recursively spawning the current executable and scraping its output.
- `codex.rs` is fairly direct despite being large; the main KISS problem is orchestration indirection, not low-level process code.

**YAGNI**
- The code generally avoids speculative trait stacks and generic abstractions.
- The main YAGNI risk is not over-abstraction; it is the inverse: several files exist as nominal modules without carrying meaningful behavioral ownership. More abstractions are not needed yet, but clearer internal command boundaries are.

# Refactoring Roadmap

## 1. Stabilize
- Add integration tests around `automate::run_workflow`, especially artifact capture, loop-stop behavior, and failure propagation.
- Introduce a stable internal result contract for commands: artifact path, final message, status code.
- Keep current user-facing output, but stop making automation depend on it.

## 2. Simplify
- Extract each service command from `main.rs` into a cohesive module entry point that owns parse/validate/run/save for that command.
- Consolidate subcommand metadata so parsing, help text, and automation capability checks share one source.
- Normalize timeout/default handling instead of repeating it per parser.

## 3. Reshape
- Rework `automate.rs` to execute command handlers through library calls where possible instead of respawning the current executable.
- Separate prompt templates from command control flow so wording changes do not affect orchestration behavior.
- After the above is stable, consider whether `codex.rs` should be split into process execution vs environment discovery; do this only if the file continues to grow.

Risk classification:
- Low-risk cleanup: consolidate command metadata, reduce repeated parsing helpers, extract prompt constants.
- Medium-risk structural extraction: move command lifecycle ownership out of `main.rs`.
- High-risk redesign: replace stdout/Markdown scraping with structured workflow results and direct internal execution.

# Quick Wins

- Replace stdout artifact scraping in `automate.rs` with a dedicated machine-readable line or file output first; this gives immediate leverage without a full redesign.
- Centralize known subcommands and option capability checks; this removes drift between `main.rs` and `automate.rs`.
- Move prompt builders out of `main.rs` so CLI dispatch and prompt content stop changing together.
- Add one integration test that proves a workflow step can produce an artifact and feed it to the next step without depending on localized phrasing.

# Open Questions / Validation Needed

- Is recursive process execution a deliberate isolation requirement, or only an implementation shortcut? That answer changes whether direct in-process command execution is acceptable.
- Does the wrapper need its current human-readable stdout format to remain stable for external consumers, or can a machine-readable side channel be added freely?
- Should workflow clean-stop semantics be based on audit text markers at all, or should the implementation-audit command emit an explicit status?
- The workspace is currently dirty (`crates/app/src/automate.rs`, `workflows/refactor.json`). Any refactor should confirm whether those in-flight changes already address part of the workflow brittleness before further reshaping.
